# 从 Claude Fable 5.1 的提示词变化，聊聊专业知识工作究竟需要怎样的“记忆”

这两天，AI 圈和极客社区不少人在关注 Anthropic 最新版本 **Claude Fable 5.1** 内置 System Prompt 的逆向提取（出自 elder-plinius 仓库）。

如果把 5.0 与 5.1 的内置提示词拿来做逐行对比，一个非常有意思的细节浮出了水面：
- **在 Fable 5.0 中**，关于记忆（`## memory_system`）的描述极其简短，仅有寥寥数行说明；
- **而在 Fable 5.1 中**，新增篇幅最大、规则最缜密的模块，赫然是长达数百行、系统级设计的 **`<memory_filesystem>`（持久化文件系统记忆）**。

Anthropic 在 5.1 中设计了类似目录结构的分类记忆（`/profile.md`, `/topics/`, `/people/`, `/areas/` 等），配备了严谨的文件增删改查工具（`memory_read`, `memory_write`, `memory_str_replace`, `memory_append`），规定了严格的 `[stated]` 事实标记与校准准则，甚至在 `<forbidden_memory_phrases>` 中下达死命令：**严禁模型在用户面前显摆“根据我的记忆……”、“我记得……”等机械说辞，要求一切以最自然、无感的方式融入交互。**

这一变化反映出一个中肯的行业事实：

> **随着基础推理能力的成熟，Agent 的工程重心正在向“长期交互质量”深入。记忆从来不是为了制造无所不知的虚幻人设，而是一套克制、可靠的上下文锚定机制——它消除了人机协作中频繁被打断的心流摩擦，是 AI 真正迈入专业工作流的基础设施。**

那么，在严肃的知识工作里，记忆到底在解决什么核心问题？为什么看似诱人的“全量记忆”在真实场景中往往适得其反？作为下一代知识工作操作系统，**ContextOS** 又是如何用轻量、自治且严谨的工程方案，实现长程交互与高难度指代消解的？

---

## 一、 为什么专业知识工作需要记忆？核心在于“指代消解”

在大众聊天应用中，大家常以为“记忆”就是记住用户爱喝什么咖啡、养什么宠物。

但在严肃的**知识工作（Knowledge Work）**与复杂业务推演中，记忆最大的价值其实非常聚焦——那就是**指代消解（Coreference Resolution）与上下文连续性**。

真实的业务协作场景往往是这样发生的：
- *“那 2020 年呢？比 2019 年少了多少？”*
- *“这个架构包含哪几个域？”*
- *“根据刚才讨论的第三条，把落地步骤拆细一下。”*
- *“那个决策中被废弃的方案叫什么？”*

在连续思考的心流中，没有人愿意在每一轮提问时，都像写公文一样把项目全称、前序背景、方案名称原封不动地敲一遍。人类天然习惯用“这个”、“刚才那个”、“它”、“第三项”来推进思考。

如果一个 AI 工具接不住这种自然的上下文：
1. **打断心流**：模型每隔两句就反问“请问您指的是哪份文件、哪个方案？”，协作体验瞬间碎成一地；
2. **答非所问**：由于缺乏对前文指代实体的锚定，模型很容易凭表面字眼在知识库里乱抓匹配，给出看似言之凿凿、实则南辕北辙的回答。

**记忆不是为了给 AI 编织虚幻的‘人格’，而是为了完成最基础的指代消解与话题承接，让多轮协作具备起码的顺畅度。**

## 二、 拒绝“全量记忆”的大水漫灌：Agent 的核心是上下文管理

市面上有些方案喜欢走向另一个极端：把用户产生的所有文字、搜索碎片全部一股脑存入数据库，每次交互不加筛选地提取一大串历史灌进 Prompt 头部，宣称做到了“全量永久记忆”。

**在 ContextOS 的架构哲学里，我们对这种“全量记忆”路线始终保持警惕。**

因为任何经验丰富的工程师都清楚一个基本事实：**Agent 的核心竞争力是精益的上下文管理（Context Management），过重的记忆反而是毒药。**

- **注意力稀释（Attention Drift）**：上下文窗口虽然越来越大，但模型的注意力分布（Attention）依然是极其敏感的计算资源。塞入过多陈旧冗余的历史，只会降低模型对当下核心任务与关键证据的理解精度；
- **时效冲突（Stale Claims）**：知识工作是动态迭代的。昨天讨论时被推翻的假设、上周临时调整的估算，如果作为记忆无脑留存，就会直接污染今天的新任务，诱发隐蔽的幻觉；
- **Token 浪费与延迟累积**：臃肿的上下文既推高了调用成本，也拖慢了交互的首字响应时间。

> **ContextOS 的思路非常明确：记忆绝不是全量倾倒，而是精细化的识别与按需注入。**  
> 真正值得系统关注的，只有三类与当前任务强相关的信息：
> 1. **指代消解**：当下句子里的代词究竟指向谁；
> 2. **重要观点**：前期讨论中已确认、不再推翻的阶段性结论；
> 3. **重要经验**：用户的专业偏好、输出语感与特定业务约束。

## 三、 ContextOS 的记忆机制：轻量记录、分层治理与 Agent 自治检索

为了在“保持敏捷”与“接住上下文”之间找到最佳平衡，ContextOS 采用了一套物理隔离与按需检索的分层机制：

```text
┌────────────────────────────────────────────────────────┐
│                   ContextOS 空间分层                   │
│                                                        │
│   [Workspace] 项目资产持久化 · 文档真源 · 主指代锚点   │
│        │                                               │
│        ▼                                               │
│   [Session]   独立任务会话 · 轻量短期窗口 (2~3 轮)       │
│        │                                               │
│        ├─► 遇到指代断点 ──► Agent 自主调取历史档案     │
│        └─► 语言与表达   ──► 按需挂载 Profile 与写作语感 │
└────────────────────────────────────────────────────────┘
```

### 1. 宏观隔离：Workspace 与 Session 各司其职
- **Workspace（工作区）**：管理长期持久的项目资料、规则与权威文档范围（`docscope`）。在 ContextOS 中，用户选中的文件与元数据本身就是**最强的主指代消解器**，天然构成了事实的边界；
- **Session（会话）**：承载具体的任务推演。不同任务在不同 Session 内独立展开，从物理结构上杜绝了跨任务历史的相互串味与干扰。

### 2. 微观精巧：Session 内轻量记录 + Agent 主动按需检索
- **默认只留极简窗口**：每轮默认只注入最近 2~3 条历史，杜绝冗余上下文带来的噪声；
- **指代消解完全交还模型（ADR-0010）**：我们早期曾尝试在服务端用启发式代码去强行改写用户的 Query，后来彻底废弃并将其移除。因为语言的指代理解本身就是 LLM 的原生强项，由 Agent 在执行回路中内聚理解，远比服务端生硬拦截更灵活、更自然；
- **Agent 自治按需调取**：当且仅当 Agent 在当前窗口发现“那个方案”、“之前的结论”等未闭合指代时，Agent 会自主决定调用轻量记忆工具（如 `conversation_history_load`），定向翻看更早的历史，把实体锚定后再发起检索。

### 3. 用户画像与写作语感：按需调用的专业修养
记忆不仅是“记住事实”，也体现在“如何表达”。
ContextOS 建立了强类型的 Layer 3 Profile 与可叠加的**写作风格库（Writing Style Library）**：
- 用户偏好（如简洁汇报、严谨学术、故事化叙述、框架提取等）被封装为风格 Skill；
- 在生成终答时，Agent 根据上下文和用户画像按需调用对应语感，使产出的文字不仅事实严谨，而且完全贴合团队或个人的思维习惯与表达调性。

## 四、 用真实数据说话：E2E 多轮指代消解评测

好机制不能停留在纸面，必须经过严苛工程测试的检验。在 ContextOS 的自动化质量矩阵中，我们建立了一套涵盖真实专业场景的多轮指代消解与记忆基准套件。

我们采用 **LLM-as-Judge 独立盲测仲裁机制**——Judge 在不预设标准答案引用的前提下，独立推断指代实体，只有同时满足 `anaphora_resolved: true`（指代消除准确）与 `answer_correct: true`（回答事实正确）两项硬指标，才算通过。

### 1. 多轮指代消解专项基准测试（Multiturn Benchmark）

| 测试维度 | 用例编号 | 轮次深度 | 评测场景与考察点 | 结果 |
| :--- | :--- | :---: | :--- | :---: |
| **近程指代** | `M1 - M2` | 2 轮 | 默认 2-prior 窗口内的直接代词顺承 | **100% PASS** |
| **远程指代** | `M3 - M5` | 4 轮 | 关键前提已滑出默认窗口，考察跨轮记忆回溯 | **100% PASS** |
| **跨文档消歧** | `M6 - M7` | 3 轮 | 行业专业词汇在不同文档间的同名指代消歧 | **100% PASS** |
| **话题切换** | `M8 - M10` | 3 轮 | 用户中途切换话题，验证旧指代不被错误继承 | **100% PASS** |
| **极限远程穿透** | `H1 - H3` | 6 轮 | 中间穿插 4 轮完全无关的文档切换，第 6 轮发起领域无关的指代提问（逼出 Agent 主动 History 回溯） | **100% PASS** |
| **汇总成绩** | **13 组复杂任务** | **2 ~ 6 轮** | **双重布尔断言（指代消除 + 回答无幻觉）** | **13/13 全通 (100%)** |

> **典型案例说明（Case H2）**：  
> 在第 6 轮提问“那个决策中被废弃的组件叫什么？”时，由于 Query 中完全不包含领域关键词，模型无法通过文档检索投机过关。测试记录显示，ContextOS 的 Agent 稳定自发触发了 `conversation_history_load` 工具，从会话深水区精准召回了对应的讨论记录，完成了 100% 的实体消解与准确回答。

### 2. 真实业务单轮与多轮联动（Golden Set 真实题库）

在真实的财务报表与企业架构设计用例中：
- **跨轮数据对比**（*“那2020年呢？比2019年少了多少？”*）：系统准确将“那2020年”消解为“2020年营业收入”，并自动结合上一轮的数值记忆与本轮检索结果，给出精确的差值比对；
- **复杂架构承接**（*“这个架构包含哪几个域？”*）：在不带主语的情况下，精准锚定上轮提到的“4A架构”，一次性完整输出业务、数据、应用、技术四大域。

## 五、 结语：不打扰，才是好设计的尺度

正如 Anthropic 在 Claude 5.1 提示词中所强调的那样：**真正成熟的系统，从来不会在回答里向用户汇报“我查了记忆库”、“我记得你之前说过”。**

记忆这项功能，最理想的状态就是“润物细无声”：
- 它不在用户不需要的时候强行刷存在感；
- 也不把大量陈旧的信息一股脑堆在当下；
- 只是当你随口说出“就按刚才那个来”或者“写得精炼一点”时，它能心领神会、分毫不差地接住你的思路。

把工作区留给真正的专业资产，把上下文留给当下的思考推演，以精益、自治的方式处理好那一小截关键记忆——这正是 **ContextOS** 在人机协作工程上始终坚持的务实姿态。
