# 仓库树开发计划：基于 PRD v0.3

日期：2026-09-10 · 状态：先行原型已运行，正式 W0/V0 未关闭

产品依据：[PRD v0.3](2026-09-10-repository-tree-prd-v0.3.md)。技术评审依据：[独立技术评审](../reviews/2026-09-10-repository-tree-prd-independent-review.md)。本计划覆盖 PRD 的 F01–F12，采用独立工程、分阶段完整交付的方式推进。

**用户已确认：Windows 原生优先。** 排期按 1 名主开发者、单机本地服务、浏览器管理界面、外部 Agent 经 MCP 使用检索能力估算。首次面向 Windows x64 本地磁盘；Linux/macOS、Windows ARM64、网络共享目录另做适配，不能用 WSL 验证替代原生 Windows 验收。

**开工决定：** 独立工程位于 `C:\Users\xingc\Documents\Codex\repository-tree`。用户明确 embedding 使用在线服务，不部署本地模型；PDF/Office 优先验证 LiteParse/AnyDoc，Docling 移出首轮安装。

**原型优先修订：** 用户在批准轻量安装后要求「先做一个原型」。已在独立工程打通浏览器导入、规则归类、在线向量检索、原文前后块和 MCP。范围及验证见[原型交付记录](2026-09-10-repository-tree-prototype.md)。当前使用 SQLite＋NumPy 精确检索与静态 HTML；LanceDB 仅做机制探针，正式后端未冻结。

**当前证据边界：** 原型不计作正式波次验收。下列 W0–W10 继续作为正式路线图，V0 通过前不宣称 W1 完成；用户要求的先行原型独立交付。实测以独立工程 `decisions/W0-environment.md` 和 `evidence/` 为准，现有仓库实现不能直接计入验收。

## 1. 交付顺序与工期

先让用户可以把一个新文件交给产品，查看它为何进入某个目录，再通过 Agent 找到原文并连续读到后续观点。此后逐层加入混合检索、复杂格式、分类辅助、完整管理界面与规模性能。

| 里程碑 | 包含波次 | 交付结果 | 累计工程人日，不含预留 |
|---|---|---|---|
| M0 原生环境与选型成立 | W0 | Windows 风险探针、引擎/传输/分发决策、契约和样本计划 | 4–6 |
| M1 最小可用产品 | W1–W2 | Markdown/TXT 的规则归档、目录索引、精确搜索和顺序续读；最小操作页面与真实 MCP 客户端接入 | 13–19 |
| M2 核心功能齐备 | W3–W4 | 混合召回、PDF/DOCX、有限内容分类、部分就绪与增量发布 | 23–34 |
| M3 P0 首发候选 | W5–W8 | 质量验证、完整管理流程、M 档性能、Windows 安装/恢复/升级验证 | 39–58 |
| M4 P1 语义主题 | W9 | 规则目录之外的跨文档语义导航，经过收益对照 | 额外 4–6 |
| 可选研究 | W10 | 主题补充召回、SVD 或量化，各自通过实验门后决定是否产品化 | 每项先设 2–3 人日探索预算 |

P0 工程合计 **39–58 人日**，另预留约 20%（8–12 人日）处理原生依赖、解析和性能风险，排期合计 **47–70 人日，约 10–14 个工作周**。一人日按约 6 小时有效工程工作估算，包含该波次设计、开发、验证和局部修复；没有把 Agent 并发直接折算成等比例缩期。等待外部资料、评审或第三方修复的时间另计。

这是一份初始估算，不是已承诺日期。W0 结束重估一次，W4 完成真实格式样本后再重估一次；不开工日期倒排，不把 P1/P2 混入 P0 首发承诺。

## 2. 独立工程与技术决策

### 2.1 默认方向

| 层 | 开发方向 | 冻结时点 |
|---|---|---|
| 运行时 | 独立 Python 工程；3.12 为兼容探针候选，最终小版本服从 Windows 依赖交集 | W0 |
| 领域模型 | Pydantic；规则、定位、版本、分类依据和工具契约在同一模型层定义 | W0 最小契约，随新增能力扩展 |
| 状态与文件操作 | SQLite、持久任务/操作账本、目标 OS 的无覆盖文件操作 | W0 探针，W1/W2 实装 |
| 检索存储 | 优先验证 LanceDB OSS + SQLite；SQLite FTS5 + sqlite-vec 为较轻对照 | W0 选定一个正式后端 |
| 文本解析 | TXT 直接读取，Markdown 用 markdown-it-py；保留源码定位 | W1 |
| 复杂文档 | PDF 验证 LiteParse，Office 验证 AnyDoc；保留结构与来源，OCR 单独处理 | W0 探针，W4 正式验收 |
| embedding | 在线服务；W0 复用 SiliconFlow Pro/BAAI/bge-m3，不部署本地模型；精排/分类单独计量 | W0 接口验证，W3/W5 冻结质量与成本配置 |
| MCP | 官方 Python SDK；优先由常驻服务暴露 Streamable HTTP，实际客户端兼容性先验证 | W0 |
| 管理界面 | FastAPI + Jinja2 + 少量浏览器 JavaScript，复用同一领域服务；无需另建完整聊天产品 | W0 确认，W2 最小流程，W6 完整流程 |
| 测试 | pytest；真实引擎临时库与 Windows 临时目录；浏览器旅程使用 Playwright | W0 约定，逐波落实 |
| 分发 | 固定 Python 环境、锁定依赖/wheel 集合、启动器；provider 配置与密钥分离 | W0 分发探针，W8 正式安装包 |

FastAPI 官方提供 Jinja2 模板集成；这是为本产品管理界面减少独立构建链的工程选择，不是性能优于 SPA 的结论。[模板文档](https://fastapi.tiangolo.com/advanced/templates/)

MCP 采用官方 SDK，并在 W0 用目标 Windows 客户端验证支持的传输与认证方式；客户端若要求 stdio，进程只作为连接同一常驻服务的协议入口，不重复启动写入者或模型实例。[官方 SDK](https://github.com/modelcontextprotocol/python-sdk)

开工后改为先验证 [LiteParse](https://github.com/run-llama/liteparse) 与 [AnyDoc](https://github.com/firecrawl/anydoc)。不能直接沿用只提取 DOCX 段落文本的 `anydoc_lite.py`，也不能只保留 Markdown 而丢弃结构与来源。Docling 仅在复杂格式出现明确质量缺口时重新评估。

### 2.2 模块边界

独立源码目录建议如下，实际工程落点在 W0 记录；本计划不在现有 Rust/Next 项目中创建依赖关系。

```text
project-root/
├── pyproject.toml / dependency lock
├── src/repository_tree/
│   ├── contracts/       # ID、版本、定位、结果和错误模型
│   ├── policy/          # 目录规则、候选分类、字段来源
│   ├── filing/          # 文件身份、移动账本、纠正与恢复
│   ├── ingestion/       # 解析、IR、chunk 顺序、有限内容抽样
│   ├── catalog/         # SQLite 目录、原文结构与快照
│   ├── retrieval/       # 已选引擎、词法/向量/精排、范围约束
│   ├── publication/     # 单写入者、发布、句柄与清理
│   ├── interfaces/      # MCP、管理 HTTP、CLI
│   └── topics/          # W9 才增加
├── prompts/             # 分类/Agent 说明的 Markdown 资产
├── web/                 # 页面模板与静态资源
├── tests/               # 单元、契约、集成、故障、Windows、UI
├── eval/                # 样本定义、问题、评分与消融
└── packaging/           # 原生启动、依赖安装与 provider 配置
```

一个常驻接口进程、一个有界后台 worker 是起点；单 root 只有一个发布写入者。MCP 和管理界面共用领域服务，浏览器请求不能自行移动文件。解析/模型计算离开接口事件循环，线程和模型副本数量服从整机预算。首版不为多后端、多 Agent 框架或插件市场设计通用抽象。

## 3. 依赖与执行规则

```mermaid
flowchart LR
    W0[W0 原生探针与契约] --> W1[W1 原文检索阅读]
    W1 --> W2[W2 规则归档闭环]
    W2 --> W3[W3 混合检索与增量]
    W3 --> W4[W4 PDF/DOCX与分类]
    W4 --> W5[W5 Agent质量门]
    W5 --> W6[W6 产品管理流程]
    W6 --> W7[W7 性能与稳定性]
    W7 --> W8[W8 Windows交付]
    W8 --> W9[W9 语义主题]
    W9 --> W10[W10 可选实验]
```

上图是单人主执行顺序。若后续增加人手，W2 之后可提前完善已稳定接口对应的页面；不能让界面开发反向绕过文件操作和发布门。本轮没有启动并行开发或额外任务。

每波交付包含可运行演示、针对性验证、已知限制与证据记录。门失败时先修复，后续仅做不依赖失败项的准备工作。部分格式或检索模式尚未实现时明确返回能力边界，不用空成功、假 embedding 或 mock 数据冒充完整能力。

## 4. 分波 WBS

### W0：Windows 原生风险探针与契约冻结（4–6 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W0.1 | 确定独立工程位置、Windows x64/本地磁盘支持范围、目标 MCP 客户端与版本 | `decisions/W0-environment.md`，无需 WSL 或现有项目服务即可启动最小服务 |
| W0.2 | 依赖与分发探针：SQLite、候选检索引擎、在线 embedding、LiteParse/AnyDoc、MCP | 在原生隔离环境完成安装、单文档处理、在线接口和工具调用；记录下载量、磁盘/RSS；干净机器验收仍在 W8 |
| W0.3 | 引擎契约探针：中文词法、过滤、空/缺失向量、未索引尾部、表版本读取与恢复 | 真实引擎验证后选定正式组合；不以 API 存在当成功，不并列保留所有候选生产路径 |
| W0.4 | 文件移动探针与公共 schema | 原生无覆盖移动、中文/空格路径、大小写冲突、占用文件、中断点；冻结 ID/版本/序号/状态/预算语义 |
| W0.5 | 准备评测分层、样本来源、规则模板和接受标准 | `eval/acceptance.json` 记录格式范围、分类误分上限/自动覆盖目标、质量容差、基准机器；未定项有负责人和关闭条件 |

**门 V0：** 首发 OS、依赖、一个检索后端、一个可用 MCP 接入和文件操作原语成立；分类质量与上线条件写入可审查的接受标准。模型最终排名可留到 W5，但输入模板、token 上限与缓存键必须可确定。探针代码可复用于产品；不能以另做一套 demo 的成功替代正式依赖组合。

### W1：Markdown/TXT 原文检索与阅读（4–6 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W1.1 | 目录登记、文档身份、稳定读取、Markdown/TXT IR 和来源映射 | 一份原文主本；文件/章节/段落可定位；解析前后修改可发现 |
| W1.2 | chunk 与 block 解耦，按原文顺序生成 seq、prev/next、parent 与范围 | 四观点跨块仍能逐块读取；编号不随相关性排序改变；重叠范围可去重 |
| W1.3 | 最小发布与查询句柄 | 选定后端的真实存储、目录/正文发布、同快照续读及过期错误；首次索引即具备中断恢复 |
| W1.4 | 三工具基本闭环：browse、literal/regex search、exact/context/section read | 实际 Windows MCP 客户端可找文件、命中块、读父级和相邻块；批量、输出预算、局部失败可见 |

**门 V1：** 从已有 Markdown/TXT 文件到 Agent 阅读完整原文可演示；literal/regex 支持稳定分页。尚无 hybrid 时在能力说明中明确不可用。对写入/发布故障做首批注入，不把一致性全部推迟到 W7。

### W2：规则归档与目录索引产品闭环（5–7 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W2.1 | 规则 Markdown/JSON 主本、schema 校验、规则命中/冲突与字段来源 | 明确区分格式、类型、角色和各类日期；同一配置通过 UI/API 与文件读取得到相同决定 |
| W2.2 | 配置收件目录、导入、有限文本抽样、确定性分类 | 收件稳定后进入处理；确定命中自动归档；歧义留待处理并给出候选/缺失依据 |
| W2.3 | 文件操作账本、源 hash、目标无覆盖、幂等和移动恢复 | planned/文件移动/manifest 发布各阶段中断可恢复；纯移动不改变原文身份 |
| W2.4 | 目录卡片、分类过滤、位置导航引用与派生清单 | 归档完成即可 browse/按名称定位；正文未就绪不冒充全文可检索 |
| W2.5 | 最小操作页面：收件状态、查看归属、纠正单文件、规则错误 | 用户无需改数据库或调用调试 API 即可完成一次导入和纠正；既有原文检索阅读仍可用 |

**门 V2 / M1：** 在原生 Windows 中，将一个含四观点的 Markdown 放入收件目录，自动归档，按目录找到它，只命中前三点时沿 next 读到第四点；之后纠正目录，原文引用仍能核验。另演示冲突文件待处理和进程中断恢复。自动文件操作只在隔离测试目录验收，不在用户业务目录做破坏性测试。

### W3：混合检索、模型配置与增量发布（5–7 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W3.1 | 实接在线 embedding，比较样本质量、API 延迟与费用 | provider/model/服务代次/template/维度/归一化进入配置和缓存键；不公开的权重版本标未知，不混用空间 |
| W3.2 | 中文 BM25、dense、RRF、范围前置、批量 query 与候选分页 | exact 向量检索作为初始正确性基准；短词/编号有确定查找路径；导航卡片不重复投票 |
| W3.3 | 目录/正文/向量分阶段就绪及双存储发布 | partial vector 仍保留全部词法原文；未发布搜索 head 不污染后续批次 |
| W3.4 | 编辑/移动/删除事件与周期校正、字段投影更新 | 已知旧版本不冒充当前；纯移动复用向量；重复事件不重复处理或误删文件 |
| W3.5 | 小候选精排基线接线与成本计量 | 能开关比较同一候选集的精排收益；最终默认模式由 W5 结果决定 |

**门 V3：** 实际模型和真实引擎完成混合检索；范围外命中、旧版本误指和假全量覆盖在回归样本中为 0。写入前、搜索表提交后、manifest 提交前后均有可复现恢复证据。S 档先通过，再做有界 M 档探测，避免首次到 W7 才发现引擎规模问题。

### W4：PDF/DOCX、复杂结构与分类辅助（5–8 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W4.1 | DOCX 与含文本层 PDF 解析适配 | 章节、阅读顺序、表格和原文定位逐格式验证；无可靠标题/坐标时保留未知 |
| W4.2 | 快速抽样与深度解析复用，扫描件/OCR状态 | 分类优先使用有限内容；正文解析复用缓存；扫描件显式报告需要 OCR，并单列成本 |
| W4.3 | 有预算的 embedding/LLM 分类辅助 | 候选目录受规则约束，返回证据位置；模型自报 confidence 不直接控制文件移动 |
| W4.4 | 日期冲突、多主题、同名异内容、相对引用/伴随资产 | 单主目录与多标签成立；未知业务日期不替换为 mtime；无法保证资产完整的移动进入待处理 |

**门 V4 / M2：** PRD 首版格式 Markdown、TXT、DOCX、含文本层 PDF、转写 Markdown 均可走完整流程。扫描 PDF 可先以明确 OCR 状态交付；若提供 OCR，则必须有独立验收结果。部分内容分类的自动覆盖率、误分率、抽样量与 token 成本同时报告。

### W5：Agent 质量、跨块完整性与默认模型冻结（4–6 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W5.1 | 建立独立开发/留出样本与合成失败集 | 按文档族隔离；真实诊断阶段目标 120 题；固定样本来源、版本、问题和评分维度 |
| W5.2 | 验证跨块连续阅读、父级展开及预算续读 | 第四点不在初始 Top-K、跨三块、后置例外、跨页、无编号等情形可比较；工具可达与 Agent 实际读到分开计分 |
| W5.3 | 比较 grep、hybrid、结构阅读、精排和目录路由 | 同模型、总 token 预算和语料版本；报告答案、引用、遗漏、轮次与读取量 |
| W5.4 | 冻结默认 embedding、精排模式和分类自动化条件 | 在已冻结接受标准下选择；不通过留出集反复调阈值，不因少量题改善宣布普遍胜出 |

**门 V5：** 采用 PRD 的分层评分；原文存在不等于答案覆盖。固定种子合成回归不能遗漏目标条件；真实任务按 W0 记录的容差验收并报告不确定性。120 题用于诊断，不自动构成小幅优越性证明；不足以定论时延长评测或保留较简单基线，不为赶进度伪造胜者。

### W6：完整管理流程与日常可用性（5–7 人日）

| ID | 任务 | 输出与通过条件 |
|---|---|---|
| W6.1 | 目录/规则设置：用途、条件、目标模板、待处理入口 | 表单与规则文件是同一配置；冲突可解释；改规则不静默搬迁存量 |
| W6.2 | 收件/待处理：批量查看、归档依据、单项/批量纠正 | 确定归档无需逐份点击；纠正单文件与保存为后续规则清楚分开 |
| W6.3 | 仓库浏览与文件详情：目录、过滤、版本、来源、原文阅读 | 可见归档/解析/向量各自状态；能展开章节、补读后文及从登记位置打开文件 |
| W6.4 | 设置和维护：MCP 接入、在线 provider 配置、任务重试、索引重建 | 错误有可执行恢复入口；索引重建保留原件、规则、用户纠正及必要操作记录 |
| W6.5 | 浏览器与接口隔离 | 本地服务绑定范围、管理写操作会话/来源校验、上传/路径校验、并发编辑冲突可验证 |

## 6. 不能延后修补的数据契约

| 契约 | 首次落实 | 关键不变量 |
|---|---|---|
| 原文主本与文档身份 | W1 | document_id 不等于路径；相同内容不同来源不自动合并身份 |
| 四类版本 | W0/W1 | source、parse、representation、publication 各自含义明确；模型/切分变化不能复用旧空间 |
| chunk 顺序 | W1 | 同文档同快照 seq 唯一；prev/next 指向原文顺序；无向量块仍可顺序读 |
| 分类依据 | W2 | role、type、各类日期与来源分开；未知不补造；局部抽样记录范围 |
| 文件移动 | W2 | 无覆盖、源 hash 核验、操作幂等、路径在受管根内；移动后中断可恢复 |
| 发布 manifest | W1/W3 | 单写入者；prepared 对读者不可见；目录过滤投影与当前搜索表成组发布 |
| 分页与预算 | W1 | 搜索候选游标、原文续读游标和相邻引用分别处理；超限显式 partial |
| 覆盖语义 | W1/W5 | 文件已枚举、正文已读、答案已覆盖分别计量；Top-K 不等于查全 |
| 当前与历史读取 | W1/W2 | 已知旧版本不冒充最新；纯移动可按 doc ID/账本核验同 hash 新路径 |

LLM 面向的分类说明、工具使用指导及运行观察写入 Markdown 资产；产品代码只装配参数和状态。业务材料和评测期望不写进产品提示或策略。运行环境报告缺失/未读/预算事实，是否继续检索由 Agent 决定。

## 7. 验证分层、性能目标与证据

### 7.1 五类证据分别报告

| 层 | 主要验证 | 不能替代的下一层 |
|---|---|---|
| 数据/领域单元 | schema、日期、路径、角色、状态转换、范围去重 | 不证明引擎和 OS 行为 |
| 真实引擎/文件集成 | Windows 临时目录、SQLite/选定引擎、真实模型、快照与故障 | 不证明 MCP 客户端和界面可用 |
| 接口/浏览器自动化 | 实际 MCP 传输、工具 JSON、预算、产品操作旅程 | 不证明答案质量或人工可理解 |
| Agent/质量评测 | 条件/例外覆盖、引用、误分与调用成本 | 不证明 Windows 分发和日常体验 |
| 原生人工验收 | 干净机器安装、真实文件、纠正和恢复、实际 Agent 宿主 | 不等于外部发布或业务效果 |

故障测试使用隔离目录和副本。合成材料用于固定失败回归，真实/公开授权材料用于泛化评估；禁止业务金标泄漏。分层准备测试，不为每个轻微 UI 文案变动新增镜像实现的测试。

### 7.2 必测旅程

1. 新文件 → 规则归档 → 目录可见 → 正文/向量逐步就绪 → MCP 问答读取。
2. 四观点在第 3/4 点间切块，第四点不在初始 Top-K；沿原文顺序读取后回答。
3. 例外位于第三个块或下一页，固定补一个块仍不足；继续读取到所需证据范围。
4. 同名异内容、同内容异来源、日期冲突和名称含“最终版”；原件不覆盖，角色不错误升级。
5. 用户纠正位置 → document_id/内容不变 → 向量复用 → 旧引用可核验。
6. 文件在归档、解析、索引或阅读期间发生变化；任务重新安排或报告明确状态。
7. 文件移动成功而数据库尚未发布时崩溃；重启不重复移动或覆盖另一文件。
8. 搜索表已写入而 manifest 未发布时崩溃；恢复后下一批不带出未提交数据。
9. 大章节、表格、重叠命中、预算不足和游标过期；可续读且不会把截止当文档结束。
10. 目录猜错或文件误分类，Agent 能通过全仓检索找到证据；显式用户 scope 仍严格执行。
11. Windows 中文/空格路径、大小写冲突、占用文件、目录链接与目标并发占用。
12. 干净安装、在线服务未配置/限流/中断、本地词法与原文可用、重建派生索引与卸载保留原件。

### 7.3 沿用 PRD 的拟性能门

| 指标 | 初始目标 | 条件 |
|---|---|---|
| 热 browse/read | P95 ≤300 ms | 已解析缓存；严格源 hash 的 I/O另列并给出总耗时 |
| 词法/过滤/向量/融合 | P95 ≤1 s | 不含 query embedding；扫描任务独立统计 |
| 在线 hybrid 工具端到端 | W3 实测后冻结 | provider 网络/服务耗时与本地搜索分开报告；原本地模型热启动 2 秒假设撤回 |
| 小文本编辑到词法可见 | 95% ≤5 s | ≤100 KB、空队列；不套用到 OCR/首次模型下载 |
| ANN 近邻一致性 | Recall@20 ≥0.98 | 与相同过滤范围 exact 对比；不等于答案召回 |
| 操作与版本正确性 | 回归/故障样本中源损坏、覆盖、错版本引用、范围泄漏、静默截断为 0 | 不能表述为所有未知输入数学上零风险 |

分类误分上限、自动覆盖目标、答案质量非劣容差在 W0 的 `eval/acceptance.json` 明确；W5 用留出集验收，不能把未定标准替换成“凭感觉通过”。解析/OCR、分类、归档、embedding、检索、Agent 生成分别记录耗时。所有数据标明硬件、依赖/模型版本、缓存、并发、样本量与输出预算。

### 7.4 每波交付收据

后续执行时，每波建立 `evidence/Wn/<run-id>/`，包含环境/版本、执行命令、退出码、测试摘要、失败样本引用、指标原始数据、人工验收范围、已知限制与下一步。日志和本地原文不自动提交或上传；版本库保留可复现配置、报告及合适的合成样本。

执行前说明预计耗时与资源成本。编译、依赖安装、脚本/批量模型调用和长测试按执行时适用的授权要求推进；本计划的工时估算不等于用户已批准运行这些命令。耗时预算用首轮观测校正，不把本次文档检查写成已跑产品测试。

## 8. 风险、决策负责人和回退范围

| 风险 | 最迟关闭 | 决策/处理 |
|---|---|---|
| Windows native wheel、解析器或引擎不可安装 | W0 | 主开发验证支持组合并记录；不以 WSL 代替，不承诺尚无支持的安装包 |
| LanceDB 过滤/空向量/快照语义不满足 | W0 | 对比 PRD 的较轻方案，选择一个后端后修订存储映射；不能绕过原文/版本契约 |
| 无覆盖移动存在竞态或文件被占用 | W0/W2 | 不自动执行未经证明的路径；保留待处理并完成 OS 级集成验收 |
| PDF 标题/阅读顺序不可靠 | W4 | 按格式路径选择和标注范围验收；未知结构不伪装成原文标题树 |
| 分类速度快但误分多，或全部待处理造成虚高准确率 | W4/W5 | 同时报误分和自动覆盖；规则/样本/辅助模型调整只用开发集 |

| 原生依赖包过大或额外下载未计量 | W0/W8 | 验证轻量格式组件的完整依赖；干净机器验证分发，不捆绑本地 embedding 权重 |
