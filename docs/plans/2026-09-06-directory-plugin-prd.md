## 0. 适用范围

定义 A 线第一版完全体（M1 闭环）及其边界。不在本文范围：B 线任何内容；credits 计费详细设计、分享包、GEO/选题看板（§10 后置）。

## 1. 背景与问题

**原点**：产品是 RAG 工作台——MCP、客户端、分享、强化检索、Agent 多路检索。发布后几乎没有流量。

**根因**（方向总结 §1）：不是检索不够准，而是工作流多了一步「搬进知识库再问」。作者自己也不用这套库——协同办公里真正在用的是桌面 Agent，不是知识库。「文件就在项目文件夹里，让 Agent 直接翻」在无感程度上打败了入库检索。

**事实基准**（方向总结 §3，产品必须对齐的现实工作流）：

1. 文件生成、下载、存放后，按项目进文件夹。
2. 用 `AGENTS.md` 约束 Agent，避免干活时乱放；目录保持相对整洁。
3. Agent 在目录里检索，精度一般、需要纠正，但仍比「入库再查」更无感。
4. **系统的真相在项目目录，不在库。**

外部佐证（R1）：2025–2026 行业共识收敛到 agentic search 优先——Claude Code 删除了早期向量管道，grep/文件系统在小型本地语料上普遍胜过预建向量索引；向量只在转述密集型查询（会议转写正是此类）与大库上有增量价值。A 线的分层设计与此吻合。

## 2. 已看清的约束（产品边界的外部事实）

- C1：模型厂商的桌面 Agent 占掉了「人开始干活」的入口。不做与人抢入口的独立客户端。
- C2：高精度检索单独成立的场景很窄；知识工作者的材料通常不多，远小于「海量超上下文」的想象。
- C3：市场分野——专业用户向大厂 Agent 集中（大厂会继续收编检索、文件、执行）；小白用 chatbot 就结束。
- C4：通用知识库售卖、封闭行业库，都会被「Agent + 网络检索 + 本地文件」挤占。
- C5：不做招标政府采购，不做 TOB 整包（那是另一个项目）。
- C6：不做平台经济；Skill 市场不是主方向——通用 Skill / 通用检索插件会被模型能力吞噬。
- C7：不卖「检索体验」——知识库不是高频打开的产品，对错是黑箱，形不成可感知体验。
- C8：不卖导航站式便捷打包——那是流量生意，且公开知识最先被模型吃掉。
- C9：「个人知识库」搜索词的意图是教程、免费工具对比、问一批材料、本地隐私、笔记所有权——不是为工作台付费。不用它当品类名获客。

## 3. 产品定义

**一句话定位**（方向总结 §4）：

> **在用户指定的项目目录里，默默跟上文件变化；Agent 随时知道现在能用什么工具；人几乎不必进你的界面。**

**形态**：目录层服务 + MCP 工具面，即「桌面 Agent 定向强化的 API 服务」。挂在用户已在用的桌面 Agent（Claude Code / Kimi Code / Cursor 等）上，复用现有本机 transport（`avrag-api` @ `127.0.0.1:18080` + `context-os-mcp`，见 `docs/desktop/LOCAL-CLIENT-MCP-CLI-AGENT-ACCESS.md`），不新造协议。

**用户路径（2026-09-06 定稿）**：

> 用户建文件夹管理文件 → 桌面 Agent 基于文件夹创建项目 → MCP 随项目/会话启动 → **插件建议 Agent 写对应的 `AGENTS.md` 内容 → Agent 写入文档** → 此后即可按规范整理工作区并调用检索能力。

**交互原则：主信道是 Agent 会话本身。**

- **接入无感**：接入目标永远由用户选择，产品不预设任何目录；最自然的目标就是桌面 Agent 自己定义的工作空间（agent cwd / project root）。MCP 随项目启动时根路径天然确定，无需文件夹选择器、无需注册流程。
- **约定由 Agent 亲写**：插件提供骨架与目录事实（文件类型分布、已有结构、已有约定内容），Agent 完成创作与合并。约定因此同时是 Agent 的原生上下文。
- **确认类交互**（归类建议、规则固化提议、大批量转写）：走 **MCP elicitation**（2025-06 规范；Claude Code / Cursor / VS Code 已支持 accept/decline/cancel 三态），但**必须有本地复核队列兜底**（Cursor Windows + HTTP 有挂起 bug；多条建议不该逐条打断）。
- **自有 UI 只剩两件、且都是可选入口**：批量复核队列、索引进度总览。用户不进去，产品也完整可用。

**完全体的 5 条定义**（方向总结 §4，逐条收录）：

| # | 定义 | 含义 |
|---|------|------|
| D1 | 目录是主本，索引是派生层 | 禁止再拷一份「入库副本」；删除索引不丢任何用户数据 |
| D2 | `AGENTS.md`（或同类约定）是产品的一部分 | 约定内容：目录结构、成品/原料位置、禁止写入区、检索顺序；乱放被纠正后**写回约定**，不只改当次回答 |
| D3 | 检索对准当前项目目录 | 评价标准是少翻错、少手动纠正，不是海量召回榜 |
| D4 | 不做默认 LLM Wiki 重编译 | 慢、重、易失真，不适合边写边变的项目目录；三元组、summary、TOC、向量全部后台静默产出 |
| D5 | 运行时索引进度是一等功能 | Agent 按就绪程度选工具：索引未好用 grep / 文件名 / 半成品 TOC，向量好了再用向量；前台不必等「入库完成」才能问 |

## 4. 目标用户与非目标用户

**目标用户**：已经在用桌面 Coding/通用 Agent 干活的知识工作者。文件按项目进文件夹，愿意（或已经）用 `AGENTS.md` 类约定约束 Agent。第一用户是作者本人（方向总结 §9：「自己先用起来」）。

**非目标用户**：用 chatbot 就结束的小白用户（C3）；招标/政府采购/TOB 整包（C5）；寻求通用知识库 / Skill 市场 / 导航站的用户（C4/C6/C8）。

## 5. 核心场景

- **S1 新项目开工**：用户建文件夹 → 在 Agent 会话里（正站在项目目录）开工 → MCP 随会话启动 → 插件建议 `AGENTS.md` 内容 → Agent 写出约定 → 后台开始静默索引。用户全程不离开 Agent。
- **S2 边写边查**：项目进行中文档持续增加。会议录音进目录 → 转写稿（说话人分离 + 时间轴）自动出现在约定位置并被索引。Agent 通过 MCP 工具查询；索引未就绪的部分用 grep / 文件名 / 大纲顶上，已就绪的走向量。用户没有「等待入库完成」的时刻。
- **S3 文件进收件箱**：下载目录（投放点）出现新文件 → 产品建议归类到某项目目录 → 用户在 Agent 会话（elicitation）或复核队列里确认后移动。默认不全自动；低置信不打扰。
- **S4 纠正写回**：Agent 把文件放错位置或找错材料，用户纠正 → 插件生成约定段落的更新稿、Agent 写回约定文件，下次同类情况 Agent 直接从约定读到规则。
- **S5 进度可见**：用户偶尔打开进度总览（或直接在会话里问 Agent），只看各项目目录索引状态（含转写任务进度）。看完即走。

## 6. 功能需求

优先级：P0 = M1 闭环必需；P1 = 闭环跑顺之后。

### F1 目录接入与约定初始化（P0）

- **无注册表**（2026-09-06 定稿）：不需要任何「已绑定目录」登记表。一个目录被视为已接入，当且仅当两个事实成立：目录里存在 Subtex 管理段落的约定文件（用户可见的标记），且应用数据目录里存在对应的索引仓。**已知根集合 = 枚举应用数据目录下的索引仓**（每个仓记录自己的根路径），不扫盘。
- **持久状态 = 索引仓**：应用数据目录下按根路径哈希分仓（派生状态：content hash、大纲、向量、约定版本、进度）。删仓 = 回到未接入状态，目录本身零影响（D1）。
- **约定初始化**：插件根据目录现状（文件类型分布、已有结构、已有 `AGENTS.md` 内容）生成**建议稿**（结构说明、成品区/原料区、禁写区、检索顺序），Agent 写入/合并进 `AGENTS.md`。已有内容零覆盖。
- **写权限边界**：所有写/移动动作校验路径落在当前会话根内；会话根由 Agent 传入（cwd / project root）并校验一致性——Agent 本身就有该目录的文件权限，插件不扩大它。未经 init 的目录上插件不发生任何写行为。
- 验收：对一个含既有文件的目录走一遍用户路径，约定文件由 Agent 写出、原有内容零丢失；应用数据目录出现对应索引仓；删除索引仓后目录文件零变化；枚举索引仓得到已知根集合（进度总览与 F6 共用此数据源）。

### F2 文件监听与后台静默增量索引（P0）

- **文件名层零自研**：v0 用查询时扫描（`rg --files` / fd 级别，小语料亚秒）+ content-hash 缓存；Windows 可借 Everything（MFT + USN Journal，`es.exe` / SDK）或 Windows Search SYSTEMINDEX（PowerShell `Search.CollatorDSO`）做全盘文件名加速；macOS `mdfind`、Linux `plocate`。内容级派生产物（大纲/向量）OS 索引给不了，仍由本管线产出。
- **监听不造轮子**：常驻监听用 Rust `notify` crate（封装 inotify / FSEvents / ReadDirectoryChangesW 三平台）+ `notify-debouncer-full` 去抖 + `ignore` crate（gitignore 语义）。watcher 会丢事件（rename、负载下溢出），必须有**周期性 mtime 调和扫描**兜底。语料小（C2），常驻 watch 是新鲜度优化项，不是前提；会话间的新鲜度靠下次会话的调和扫描恢复。
- **音频转写前端（2026-09-06 并入，复用 asr-filetrans 链路）**：目录内出现音频文件（wav/mp3/m4a/aac/ogg/flac/opus/wma/amr）→ 后台云端转写 → **成品 `transcript.md` 写回目录约定位置**（说话人分离 + 按会议绝对时间轴的 Markdown；转写稿是用户的成品、目录的一等文件——主本的一部分，不是索引私产），随后按普通文档进入索引管线（说话人切换/时间段是天然切分边界，R1）。
  - 链路复用仓外独立工具 `asr-filetrans`（百炼 `qwen-audio-3.0-asr-flash-filetrans` 异步任务 + VPS 临时托管；句级时间戳、字级置信度；全流程幂等、断点续跑；已经 3h40m 真实录音验证）。v0 直接调用其既有 CLI（`bin/transcribe.sh run/status/merge/cleanup`），工具保持独立维护（`/home/chuan/asr-filetrans/AGENTS.md`）；是否吸收为 avrag-rs 内模块留待技术设计裁决。
  - 凭据零配置：沿用其 `.env` 链（`asr-filetrans/.env` → `avrag-rs/.env` 的 `DASHSCOPE_API_KEY` / `VPS_MAIN_*`），不新设凭据入口。
  - 中间品（转码 mp3、任务 JSON）放索引仓/临时区，不进项目目录；原始 `results/*.json` 保留供二次分析（24h 过期的 transcription_url 须完成即下载，链路已处理）。
  - 计费透明：按时长走百炼账户（F7 首个耗材项）。日常零星录音默认自动转写；**单批累计超过阈值（默认 2 小时）先经 elicitation/复核队列报量级、确认后跑**（防账单冲击，沿用 asr-filetrans 已知坑 8 的惯例）。
- 其余索引产物（三元组、summary、TOC/大纲、向量）全部后台静默生成，复用 avrag-rs 现有 ingestion 管线能力；**不产生第二份文件副本**；**索引集中存放在应用数据目录的索引仓**（2026-09-06 决策 B-②），不污染项目目录、不被 git 跟踪；索引可整体重建。
- 索引栈设计要点（R1）：切分全部结构感知（markdown 标题 / PDF 章节 / 转写的说话人·时间段；chunk 带 heading-path 元数据，杜绝定长窗口）；增量用 per-file content hash（不引入 Merkle tree）；词法+向量做单库混合（SQLite FTS5 bm25 + 向量扩展 + RRF），不引入独立向量 DB；reranker 留接口后上（本地 cross-encoder ~300ms，是 10³ 文档下性价比最高的质量杠杆）。
- 索引过程不阻塞任何查询路径；资源占用有节制（§8 NFR）。不做 LLM Wiki 式全量重编译（D4）。
- 验收：向已接入目录放入一批新文件，不加干预，索引产物在后台逐步就绪；放入一段真实音频，约定位置出现说话人分离的时间轴 transcript.md 且可被检索；索引全部落在应用数据目录；删除索引仓后目录文件零变化、索引可重建；watcher 暂停期间的变化经调和扫描被补齐。

### F3 运行时索引进度与工具分级暴露（P0）

- 每个已接入目录暴露机器可读的索引就绪状态（按产物类型分级：文件名/grep 可用 → 大纲可用 → 向量可用；转写任务含在途进度）。
- **工具集固定，不就绪即隐藏**（R1 证据：agent 靠工具描述选工具，动态增删工具列表会提高选错率）。将就绪状态写进**工具描述与返回**：如 "semantic index building, N/M files ready; outline search recommended meanwhile"；检索结果带 `matched_via` 标签（精确命中 vs 放宽召回）与出处路径，截断时给出下一步指引。
- 验收：接入目录后分批放文件，任一阶段工具清单稳定、描述中的就绪状态准确；任一阶段提问都有可用检索路径。

### F4 MCP 工具面（P0）

- 桌面 Agent 通过 `context-os-mcp`（复用现有 transport）发现并使用 Subtex 工具。不新造第二套协议。
- 工具集合覆盖：init/目录状态查询（root 参数，首接触即接入）、约定建议稿生成与写回稿生成（配合 F1/F5，Agent 负责实际写文件）、分层检索（词法 → 大纲 → 向量混合）、收件箱建议查询与确认（配合 F6，elicitation + 队列兜底）、转写任务提交与进度查询（配合 F2 音频前端）。
- **大纲层是向量就绪前的全局定位能力**（R1）：模仿 Aider repo map——token 预算化（1–2k tokens）的「文件名 + 标题树 + 一句话摘要」，让 Agent 先拿结构概览再深入。
- **向量层定位为第三层补充**（R1）：语料小，词法是默认主力；向量的正当场景是转述密集型提问（会议转写、概念性问答）。混合检索内部 BM25+向量+RRF。
- 验收：在一个真实桌面 Agent（Claude Code 或 Kimi Code）中配置后，Agent 能发现工具、完成 init、拿到约定建议稿、查到目录状态与就绪度、完成一次大纲查询和一次混合检索，返回带 `matched_via` 与出处。

### F5 纠正写回约定（P0）

- 提供「把本次纠正写回约定」的工具：输入是一次纠偏（文件应放哪、某类材料应去哪查），输出是约定文件 Subtex 管理段落的**更新稿**；Agent 审阅后写回约定文件（纯文本、可回退）。
- 与 F6 联动：同一归类模式被用户接受 N 次后，提议「固化为约定/规则」，用户一键确认（R2 建议 6）。
- 验收：模拟一次「乱放 → 纠正 → 写回」，约定文件出现对应规则；此后 Agent 读取约定能拿到该规则。

### F6 收件箱与建议归类（P1）

策略按 R2 调研定稿（最高保守标准）：

- **三档置信**：高置信也仅在「用户显式开启全自动」且目标在已接入项目根内部时直通；中置信 → 建议+理由，等确认；低置信 → 静默留在收件箱，不发通知打扰。
- **批量复核队列是家，通知只是入口**：digest 式批量确认；单条轻量确认走 Agent 会话 elicitation 或 OS 通知（接受/换目标/忽略），过期自动进队列。
- **建议目标集小而固定**：只对已接入项目根（枚举索引仓，≤10）做建议；映射不上 = 留收件箱；绝不新建目录。
- **规则先行，AI 殿后**：用户自写的确定性规则（扩展名/名称/来源）命中可自动执行；AI 建议必须确认；「正文关键词」类规则标注为易碎。
- **确认即训练**：accept/reject 写回建议模型；N 次接受同模式 → 提议固化（接 F5）。
- **永远可撤销 + 建议附理由与预览**；onboarding 明示训练期（前几周需要纠错，越纠越准）。
- 只监视指定投放点，不监视整盘（§7 硬规则）。**投放点列表是本功能唯一的用户配置**，存应用数据目录的小配置文件。
- 验收：投放点出现新文件后按置信档位产生对应行为；未确认前文件不移动；全自动仅在选项开启且目标在已接入项目内时生效；任何移动可一键撤销。

### F7 credits 账本（P1，闭环跑顺后立项）

- credits 只对应真实耗材：**录音转写（百炼 filetrans，按时长计费——首个耗材项）**、embedding 等 API 调用。
- **云端代付，不做 BYOK**：桌面 Agent 侧零感知——用户不在 Agent 会话里看到任何配置 key、余额警告类打扰；账本查询留在自有 UI / B 线账户体系。大批量转写的「报量级再跑」（F2）是防账单冲击的安全阀，不是费用打扰。
- 分享、GEO、选题看板不摊进同一份 credits（B 线事务）。
- 验收（立项时细化）：每一笔 credit 扣减可对应到一次真实 API 耗材调用；Agent 会话全程无费用可见元素。

## 7. 硬规则与边界

方向总结 §5、§8 全量收录，违规则视为产品缺陷：

1. 只监视会话接入的项目目录与用户指定的投放点；**不监视整盘**。（OS 级文件名索引的**只读查询**不构成监视，见 F1/F2。）
2. 默认「收件箱 + 建议归类 + 确认后移动」；全自动仅选项且限已接入项目根内部。自动移动一旦分错项目，信任归零——此功能按最高保守标准设计。
3. 目录是主本：禁止入库副本；索引是派生层，集中存放于应用数据目录索引仓，可删可重建；转写稿等成品写回目录（主本），中间品留索引仓/临时区。
4. 不做默认 LLM Wiki 重编译路径。
5. **明确不做**（方向总结 §8）：
   - 再做一个跟人抢入口的独立客户端当主产品
   - 给人用的通用知识库 / RAG 工作台定位
   - 给所有 Agent 的免费检索插件当生意
   - Skill 商店 / 双边知识市场当主航道
   - 全盘自动归档
   - 默认走重 Wiki 编译
   - 客服、刷题、招标、TOB 整包
   - 用「个人知识库」当品类名去获客

## 8. 非功能需求

- **N1 无感**：不用上传、不用注册、不用等索引完才能问；Agent 会话里不出现配置/费用类打扰（F7）；产品存在感趋近于零（确认归类与进度查看除外）。
- **N2 本地优先与隐私**：目录与索引默认留在本机；满足「本地隐私、笔记所有权」意图（C9）。音频转写是唯一默认上云的处理（用户已顺手的既有链路），音频仅在 VPS 临时托管、转写完成即清理；其他任何上云动作需独立产品决策。
- **N3 资源节制**：后台索引对本机 CPU/IO/内存占用有上限与退让策略；遵守本仓 WSL 资源约定（`docs/agent/rust-resources.md` 精神）。
- **N4 可观测**：索引进度、转写任务、失败、耗材可查询（机器可读，供 F3、进度总览、Agent 会话查询共用）。

## 9. 成功度量

不做召回榜式指标（D3）。度量三件事：

1. **自用成立**：作者每天真实使用（方向总结 §9 的硬标准）。
2. **少翻错**：Agent 检索结果需要人工纠正的频次下降（以 S4 写回次数与纠偏记录为代理指标）。
3. **少手动纠正目录**：S3 建议归类的确认通过率上升、误移动为零。

## 10. 产品线与里程碑

**A 线（本文，Subtex —— 桌面 Agent 定向强化 API 服务）**：

- **M1（下一件只做的一件事）**：对一个用户选定的文件夹完成闭环——约定初始化（插件供稿、Agent 亲写）→ 后台静默索引（含音频转写前端）→ 按进度暴露工具 → 纠正写回约定。覆盖 F1–F5。作者自己先用起来（首个目录由作者在自用 Agent 工作空间中选定）。**开发计划：`docs/plans/2026-09-06-subtex-m1-dev-plan.md`**（W0–W5 波次 + 验证门 + 总验收标准；2026-09-07 W0–W5 开发完成，遗留项见计划 §9 实施记录）。
- **M2**：F6 收件箱与建议归类（确认制 + elicitation + 复核队列）。
- **M3 及以后（M1 跑顺前不立项）**：F7 credits 账本；分享若保留，最多是「整理好的项目目录一键打成可分享包」。

**B 线（现有工作台 → 订阅制知识经济营销工作台）**：并行开发中；原商业模式（ADR-0010：可分享 Workspace 订阅、代购、邀请码）保留；GEO/趋势/选题看板属 B 线，不进 A 线任何里程碑（方向总结 §7：客户是「把知识当货卖的人」，节奏不同）。

**两线关系**：共享底层检索技术（avrag-rs ingestion / 检索栈），各自独立发展；A 线的「一键打成可分享包」是未来两线的接缝，不是本期需求。

## 12. 决策记录与剩余开放问题

**已裁决（2026-09-06）**：

- O1 商业模式关系 → **并存**：原商业模式保留；A/B 两线是基于底层检索技术的两个新产品方向，各自独立发展。
- O2 容器法则 → **改 AGENTS.md**：T7 已修订（§11），无需另起 ADR。
- O3 credits 挂钩 → **云端代付，不做 BYOK**，Agent 侧尽量无感。
- O4 命名 → **定名 Subtex**（拉丁 subtexere·在下方编织；不用中文名）。落地前实测 npm / crates / GitHub / `subtex.dev` 可用性。
- O5 现有工作台处置 → **并行开发保留**（即 B 线）。
- O6 目录选择 → **由用户选择，产品不预设**；产品直接在桌面 Agent 定义的工作空间上工作（agent workspace 即一等接入目标）。
- O7 注册表 → **取消**：用户路径（文件夹 → Agent 建项目 → MCP 启动 → 插件供稿 → Agent 写约定）不需要绑定登记；「已接入」由目录内约定文件 + 应用数据索引仓两个事实推断；已知根集合 = 枚举索引仓。唯一保留的用户配置是 F6 投放点列表（P1）。
- O8 音频转写 → **集成 asr-filetrans 既有链路**：v0 直接调用其 CLI（仓外工具独立维护）；成品 transcript.md 写回目录约定位置（主本），中间品留索引仓/临时区；凭据沿用 `.env` 链零配置；大批量（>2h）先报量级再跑。是否吸收为 avrag-rs 内模块留待技术设计。
- 索引存储位置 → **集中应用数据目录**（按根路径哈希分仓，不污染项目目录）。
- 约定文件形态 → **复用 `AGENTS.md`**，插件供稿、Agent 亲写 Subtex 管理段落。
- 文件名检索层 → **借 OS 索引/快速扫描，零自研**（F2）。

**剩余开放**：无阻塞项。落地前的小事：Subtex 包名/域名实测；M1 首个自用目录由作者在自用 Agent 工作空间中选定（无需预设）；转写链路是否吸收进 avrag-rs 在技术设计时裁决。
